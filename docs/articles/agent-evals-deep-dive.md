# Agent Evals 深度解析：别再靠"感觉不错"发布智能体

> 从轨迹评估到环境状态金标准，从 pass^k 到 LLM-as-judge 三大偏置——把"感觉不错"变成"我们知道什么变了"

*2026-11-24*

---

## 引言：单次补全和过程是两种生物

博客写过 LLM 评估（基准与 prompt 评测）和 LLM 可观测性（生产治理）。但那两篇的对象是"一次调用"——输入进、输出出、打个分。**Agent 是另一种生物**：它规划、调工具、读结果、从自己的错误中恢复（或者不恢复）。

只看最终答案评估一个 agent，就像**只看最后一手棋评判整盘棋局**。两个 pass 率相同的 agent 也不等价：一个 40 轮完成、烧掉 20 倍 token；一个 12 轮干净收尾。一个中途吞掉了三次工具错误硬撑到终点；一个第一次报错就优雅重试。

更阴险的是：**agent 宣布胜利的语气总是很流畅**。"我已成功修复该 bug"——文件没改、测试没跑、行没插入。agent 的自我报告不是证据，是输出。

这篇拆解 2026 年 Agent 评估的完整工程体系：双层评估、环境金标准、指标、LLM-as-judge 的偏置与校准、基准地图、评估驱动开发的闭环。它正好回答最近三篇 Harness 系列（Deep Agents、DSH、多智能体）留下的悬而未决的问题：**harness 造完了，怎么知道它变好了？**

---

## 一、双层评估：轨迹 + 结果，一个都不能少

Agent 评估在两个层级上同时展开：

```
                    一次完整 Agent 运行
  ┌────────────────────────────────────────────────┐
  │  轨迹 (Trajectory)                              │
  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌───────┐ │
  │  │ 模型轮次 │→│ 工具调用 │→│ 工具结果 │→│ 重试…  │ │
  │  └─────────┘ └─────────┘ └─────────┘ └───────┘ │
  │        └───────── 全部记录成可回放轨迹 ─────────┘ │
  └────────────────────────┬───────────────────────┘
                           ▼
  ┌────────────────────────────────────────────────┐
  │  结果 (Outcome)                                 │
  │  ❌ 问 agent: "完成了吗?" → "是的!" (流畅地撒谎) │
  │  ✅ 查环境: 文件存在? 测试通过? 数据库行已插入?   │
  └────────────────────────────────────────────────┘
```

**结果层：查环境状态，不查 agent 的嘴。** 任务完成的金标准是**可执行检查**：文件存在、`pytest` 通过、数据库里的行数对、HTTP 端点返回了正确结构。agent 说"我做完了"在评分系统里权重为零。

**轨迹层：评估路径的质量。** 三件事：

- **步数与效率**：完成率不变但步数上涨 = 效率在退化（这是 harness 变质最早的信号——Deep Agents 篇讲过，中间件配置错误常常表现为"还能完成任务但越跑越笨"）
- **循环检测**：同参数重复调用同一工具超过 N 次 = 空转（Harness 篇讲的"循环控制"在此量化）
- **被吞掉的错误**：工具返回失败但 agent 没重试、没上报、当没看见——把失败喂进轨迹中段，看 agent 是重试、报告，还是**幻觉出一个结果**

两层缺一不可：只看结果，你会放过"碰巧蒙对"的 agent；只看轨迹，你会纠结过程完美但根本没做完任务的运行。

## 二、工具调用正确性：收益密度最高的检查

轨迹评估里最机械、也最高产出的部分是**对 trace 的代码断言**（不需要任何 LLM 裁判）：

| 检查 | 抓什么失败 |
|-----|-----------|
| **选对工具** | 意图是搜索却调了写入工具 |
| **参数抽取正确** | ID、日期、过滤条件从上下文提取错误——**agent 在这里静悄悄地失败** |
| **顺序约束** | 先搜索后回答、先读后写；跳步 = 后面全错 |
| **错误处理** | 喂一个工具失败，验证它重试或上报而非编造 |

这些是写在测试代码里的断言，跑一次的成本几乎为零。**把 LLM 裁判省下来，只回答代码回答不了的问题**（"这个计划合理吗？"）——这是评估成本控制的第一原则。

## 三、环境评估：金标准

对任何**会改变状态**的 agent（写代码、改数据库、发邮件），终极评估形态是：

```
 ① 确定性搭建            ② agent 运行            ③ 程序化评分
 ┌─────────────┐        ┌─────────────┐        ┌─────────────┐
 │ 沙箱容器      │  启动   │ agent 全程   │  结束   │ 可执行检查:  │
 │ 种子数据库    │ ──────► │ 在环境里     │ ──────► │ 测试套件     │
 │ Mock API     │        │ 自由行动     │        │ 状态断言     │
 │ 预置文件      │        └─────────────┘        └─────────────┘
 └─────────────┘          （不做任何干预）          （不做人工判断）
```

三个特征：**确定性搭建**（每次运行环境一模一样）、**agent 自由行动**（不约束路径，只看终局）、**程序化 teardown 与评分**（评分器没有任何模糊空间）。

它比"黄金对话集"（golden transcripts）贵得多，但对状态变更型 agent 值回票价——**对比答案文本永远测不出"行到底插没插进去"**。

 τ²-bench 的设计值得偷学：**模拟用户**（一个 LLM 扮演客户来回对话）+ **政策文档**（政策合规作为评分维度）——客服型 agent 的行为不能只看任务完成，还要看"全程没违反退款政策"。

## 四、指标：三个数字看穿一个 agent

**pass@1 vs pass^k——两种完全不同的承诺。** pass@1 是"k 次里至少成功一次"（创造力场景）；**pass^k 是 k 次全部成功**（可靠性场景，τ-bench 提出）。生产 agent 要的是后者：用户不在乎你的客服 agent 十次里有九次很好，**在乎的是落到自己头上那次**。同一个 agent，pass@1=0.9 和 pass^8=0.43 可以同时成立——非确定性下，可靠性的衰减是指数级的。

**steps-to-completion——效率的心电图。** 通过率稳定、步数缓涨，是 harness 退化的最早信号（上下文压缩配置坏了、工具 schema 变了导致模型反复试探）。单独盯通过率看不见它。

**cost-per-success——决定能不能上线的数字。** 成功率 90% 但每次成功成本 $2 的 agent，在多数商业场景等于不可用。把 token、工具调用、时间全部折算进"每次成功的成本"，是唯一能和业务对话的指标。

**非确定性下的统计纪律**：每个用例跑 N 次（3~5 起步）报均值，发布对比用配对统计；**锁定 CI 里的模型版本**——模型升级不是"免费提升"，是要过全套评估门的变更（这个认知来自惨痛教训：模型悄悄升级把 agent 的工具调用习惯改了，通过率掉了 15 个点没人知道为什么）。

## 五、LLM-as-Judge：好用，但带三颗雷

代码断言覆盖不了的维度（"摘要忠实吗？""语气对吗？"）需要 LLM 裁判。但它有三份**有论文记录的偏置账单**：

| 偏置 | 表现 | 解法 |
|-----|------|-----|
| **位置偏置** | 成对比较偏爱第一个选项 | 双序评判各跑一次取平均 |
| **冗长偏置** | 同质量下更长的输出得分更高 | 长度上限；rubric 里明确"简洁不扣分" |
| **自我偏好** | 模型偏爱自家家族的文风 | 裁判用与生成器不同的 provider |

两条铁律凌驾于偏置之上：

1. **rubric 必须具体到可执行**："每个数值论断是否都有来源引用——逐条 yes/no"，而不是"质量打 1-10 分"。模糊 rubric 是裁判幻觉的温床
2. **永久的 5~10% 人审抽样**：裁判是扩展人力的工具，不是免监督的权威——**先用 100~200 条人工标注校准**（算裁判与人类的一致率），rubric 改了就重新校准。博客 RAG 评估篇讲过 judge 的坑，Agent 场景把它放大了：裁判要读的东西从一段文本变成了一条完整轨迹

## 六、分离评估者：fresh context 抓"看起来做完了"

轨迹和结果都测完，还有一类失败两法皆盲：**产出"像完成"但实际错误**——代码结构完美但逻辑反了、报告写得头头是道但数字是编的。

解法在博客多智能体篇讲过（Evaluator-Optimizer 模式：**评估独立性 > 评估能力**）：**用全新上下文的另一个 agent 实例来验收产出**。它不知道第一个 agent 经历了什么、没有"沉没成本"的上下文惯性，只拿到任务书和产出，从零判断。

```
 生产 agent(完整轨迹/压缩历史/工具调用)──► 产出
                                            │
 评估 agent(零共享上下文) ◄── 任务书 + 产出 ──┘
   只做一件事: 假装自己是第一次接触这个任务的人,
   验收产出是否真正完成它
```

Deep Agents 的 context evals 用了同款思想：**故意在任务中途触发摘要，然后检查 agent 是否还记着自己的目标**——用受控实验暴露"harness 压缩弄丢了任务意图"这类结构性失败。

## 七、基准地图 2026：选模型看它们，测产品别看它们

公开基准的正确用法：**选底模、偷任务设计**。它们几乎不预测你自己领域上的表现。

| 基准 | 测什么 | 值得偷的设计 |
|-----|--------|------------|
| **SWE-bench Verified** | 真 GitHub issue 修复（人审 500 题） | 隐藏单元测试做状态检查 |
| **SWE-bench-Live** | 自动更新的多语言/多 OS 变体 | **防污染设计**：数据持续追加；2026/08 起**提交必须附 rollout 轨迹**供审计——防"只给问题陈述却偷喂 ground truth"的作弊 |
| **Terminal-Bench 2.0** | 89 个真容器终端任务 | **最干净的模板**：手工审计 + 可执行测试评分 |
| **GAIA** | 通用助理（搜索/推理/工具） | 答案简短无歧义，适合自动评分 |
| **τ²-bench** | 工具 + 政策 + 模拟用户 | **pass^k 可靠性**、用户模拟、政策合规维度 |
| **OSWorld / WebArena** | 桌面/浏览器 computer use | 可重置环境 + 程序化检查 |
| **BFCL** | 函数调用准确率 | 组件级工具调用测试 |

两个必须懂的概念：

**饱和（Saturation）**：前沿模型在 SWE-bench Verified 已到 80~90 分，基准失去区分"好"与"极好"的能力——于是社区长出更难的变体（Live、Windows、多语言）。选基准要看它在不在饱和曲线上。

**真实世界差距**：基准高分 ≠ 你的产品好用。你的数据形状、你的边缘案例、你用户的奇怪措辞，任何基准都不覆盖。**你的自有评估集才是发布决策的依据**——公开基准只回答"选哪个模型"。

顺带一提 LangChain 在 Terminal-Bench 上从 top 30 爬到 top 5 的路径：**没换模型，纯 harness 迭代**——评估驱动开发的最佳公开案例（Deep Agents 篇讲过的激进压缩实验就是这个爬坡过程的一部分）。

## 八、评估驱动开发：把"感觉"换成"知道"

核心实践只有一条：**永远不要浪费一次失败**。

```
        ┌────────────── 离线（发布门） ──────────────┐
        │                                          │
        │  冒烟套件(20-30题,确定性检查) → 每 PR 跑    │
        │  完整套件(全维度,N次试验) → 每晚+发布前     │
        │  门禁: 通过率降幅不越置信区间 / 零严重违规   │
        │        / cost-per-success 在预算内         │
        └──────────────▲───────────────────────────┘
                       │ 生产失败 → 新测试用例
        ┌──────────────┴──── 线上（监控） ───────────┐
        │                                          │
        │  全量 trace(OTel span: 每次LLM/工具调用)   │
        │  显式信号: 👍/CSAT/投诉                    │
        │  隐式信号: 转人工率/放弃率/24h重复联系      │
        │  健康信号: 工具错误率/循环检测/步数离群/p95  │
        │  采样裁判: 1~5%会话 + 全部转人工会话        │
        │                                          │
        │  发布节奏: shadow mode → canary → A/B     │
        └──────────────────────────────────────────┘
```

线上和离线**必须连成环**：被标记的 trace 进入人审队列 → 失败沉淀为评估用例 → 离线门拦住下一个携带同样缺陷的版本。断了这个环，你的评估集永远只覆盖你想象得出的失败，而不是真实发生的失败。

启动顺序（别贪全）：

1. **先埋 trace**——写任何指标之前，先把每次 LLM/工具调用的输入输出结构化落盘（JSONL、可回放、可 grep）。**看不见的东西评估不了**
2. **读 50~100 条 trace 做失败分析**——建失败分类账，数出 top 3 失败类别
3. **30~100 个任务的小评估集**（带状态检查）+ 每题 3~5 次试验
4. 给 top 3 失败类别加**定向轨迹/组件测试**
5. 每个**不可逆工具**和每个**不可信数据源**加安全测试（注入攻击——呼应博客安全护栏篇）
6. 校准过的裁判只在必要处上线
7. CI 门禁 + 线上采样闭环

## 九、成熟度阶梯：你在第几级

| 级别 | 形态 | 能抓住什么 |
|-----|------|-----------|
| **L0** | 跑起来、肉眼看、上线 | 什么都抓不住（每个 demo 都在这级） |
| **L1** | 确定性门：测试 + lint 钩子 | 尴尬级错误（一下午的投入） |
| **L2** | 分离评估者（fresh context 验收） | "看起来做完了" |
| **L3** | 评估集 + 全量 trace | 变更变成可度量的（"我们知道什么变了"） |
| **L4** | 持续评估：线上采样 + 漂移告警 + 成本仪表盘 | 生产退化在用户投诉之前 |

每一级抓住上一级**结构性抓不住**的失败。多数团队停在 L0；L1 只差一个钩子；L3 是"我们觉得它能用"变成"我们知道改动的影响"的分水岭。

## 十、避坑清单

1. **给最终消息打分而不是给最终状态打分**——agent 宣布胜利的语气永远流畅
2. **只报 pass@1 不报 pass^k**——可靠性衰减是指数的，均值掩盖尾部
3. **judge 没校准就上量**——先 100 条人工标注算一致率；rubric 一改重新校准
4. **rubric 写"质量 1-10 分"**——模糊 rubric 喂养裁判幻觉；写到逐条 yes/no 的粒度
5. **评估集一次建好不再长**——生产失败是免费的高价值测试用例，浪费它就是双倍损失
6. **CI 不锁模型版本**——模型静默升级 = 未经评估的变更混进生产
7. **盯通过率不看步数**——步数缓涨是 harness 退化的最早心电图
8. **环境评估省略确定性搭建**——环境每次不一样，跑分波动你分不清是 agent 还是环境
9. **公开基准当产品验收**——基准选模型可以，测产品必死；真实世界差距永远存在
10. **L0 直接跳 L4**——没有 trace 的采样裁判是空中楼阁；阶梯要一层层爬

## 十一、结语：瓶颈从来不在模型

博客 Harness 篇的结论是"Harness 决定上限"；这篇补上另一半：**在任何 agent 循环里，瓶颈是评估器（verifier），不是模型**。模型三个月一代际，评估体系是跟着你的产品长出来的、无法被下一代模型白送的资产。

最锋利的一句话留给结尾：**别再要求模型更可信，去建造那个不需要信任模型的系统。**（Stop asking the model to be more trustworthy — build the system that doesn't need to trust it.）评估体系就是这个"不需要信任"的系统本身。

至此博客 Agent 工程链路完整闭环：**造车（Harness）→ 驾驶（编排/记忆/工具）→ 验车（本文）**。
